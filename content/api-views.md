In [DRF: Your First API](/learn/drf-first-api) you wrote function-based API views. DRF also offers **class-based** API views, in three levels of abstraction. Each level writes more code for you:

| Level | Class | You write |
|---|---|---|
| 1 | `APIView` | A method per HTTP verb: `get()`, `post()`... |
| 2 | `GenericAPIView` + mixins | Which actions to include |
| 3 | Concrete generic views (`ListCreateAPIView`...) | Just `queryset` and `serializer_class` |
| 4 | ViewSets (next chapter) | One class for all actions, URLs generated by a router |

We'll build the same two endpoints at each level:

- `GET /api/players/` (list) and `POST /api/players/` (create)
- `GET`, `PUT`, `PATCH`, `DELETE /api/players/<pk>/`

## Level 1: APIView

`APIView` is DRF's version of Django's `View`. HTTP methods are dispatched to methods of the same name, and you get DRF's `Request`, `Response`, authentication, permissions and throttling.

```python title="players/views.py"
from django.shortcuts import get_object_or_404
from rest_framework import permissions, status
from rest_framework.response import Response
from rest_framework.views import APIView

from .models import Player
from .serializers import PlayerSerializer


class PlayerList(APIView):
    permission_classes = [permissions.IsAuthenticatedOrReadOnly]

    def get(self, request):
        players = Player.objects.select_related("team")
        serializer = PlayerSerializer(players, many=True, context={"request": request})
        return Response(serializer.data)

    def post(self, request):
        serializer = PlayerSerializer(data=request.data, context={"request": request})
        serializer.is_valid(raise_exception=True)
        serializer.save(owner=request.user)
        return Response(serializer.data, status=status.HTTP_201_CREATED)


class PlayerDetail(APIView):
    permission_classes = [permissions.IsAuthenticatedOrReadOnly]

    def get_object(self, pk):
        return get_object_or_404(Player, pk=pk)

    def get(self, request, pk):
        return Response(PlayerSerializer(self.get_object(pk)).data)

    def put(self, request, pk):
        serializer = PlayerSerializer(self.get_object(pk), data=request.data)
        serializer.is_valid(raise_exception=True)
        serializer.save()
        return Response(serializer.data)

    def patch(self, request, pk):
        serializer = PlayerSerializer(self.get_object(pk), data=request.data, partial=True)
        serializer.is_valid(raise_exception=True)
        serializer.save()
        return Response(serializer.data)

    def delete(self, request, pk):
        self.get_object(pk).delete()
        return Response(status=status.HTTP_204_NO_CONTENT)
```

```python title="players/urls.py"
from django.urls import path
from . import views

urlpatterns = [
    path("players/", views.PlayerList.as_view(), name="player-list"),
    path("players/<int:pk>/", views.PlayerDetail.as_view(), name="player-detail"),
]
```

**Use `APIView` when** an endpoint doesn't map to simple CRUD: a "send password reset" endpoint, a dashboard summary, a webhook, a calculation.

```python
class StatsView(APIView):
    def get(self, request):
        from django.db.models import Avg, Max, Sum
        return Response(Player.objects.aggregate(
            total_runs=Sum("runs"), best=Max("runs"), average=Avg("runs"),
        ))
```

### Per-view policy attributes

Every DRF class-based view accepts these, overriding the global `REST_FRAMEWORK` settings:

```python
class PlayerList(APIView):
    authentication_classes = [JWTAuthentication]
    permission_classes = [IsAuthenticated]
    throttle_classes = [UserRateThrottle]
    renderer_classes = [JSONRenderer]
    parser_classes = [JSONParser]
```

## Level 2: GenericAPIView + mixins

Notice how the APIView code repeats: get the queryset, pick a serializer, validate, save, respond. `GenericAPIView` stores the common pieces as attributes, and **mixins** provide the action methods.

```python
from rest_framework import generics, mixins


class PlayerList(mixins.ListModelMixin, mixins.CreateModelMixin, generics.GenericAPIView):
    queryset = Player.objects.select_related("team")
    serializer_class = PlayerSerializer

    def get(self, request, *args, **kwargs):
        return self.list(request, *args, **kwargs)

    def post(self, request, *args, **kwargs):
        return self.create(request, *args, **kwargs)
```

| Mixin | Provides | Typically wired to |
|---|---|---|
| `ListModelMixin` | `.list()` | GET on a collection |
| `CreateModelMixin` | `.create()` → 201 | POST |
| `RetrieveModelMixin` | `.retrieve()` | GET on one object |
| `UpdateModelMixin` | `.update()`, `.partial_update()` | PUT, PATCH |
| `DestroyModelMixin` | `.destroy()` → 204 | DELETE |

`GenericAPIView` attributes and hooks:

| Attribute / method | Purpose |
|---|---|
| `queryset` | The base queryset |
| `serializer_class` | The serializer to use |
| `lookup_field` | Field used to fetch one object (default `"pk"`) |
| `lookup_url_kwarg` | URL keyword name if different from `lookup_field` |
| `pagination_class`, `filter_backends` | Paging and filtering ([next chapters](/learn/filtering-pagination)) |
| `get_queryset()` | Override to filter dynamically, e.g. by user |
| `get_serializer_class()` | Choose a serializer per request |
| `get_object()` | Fetches one object **and runs object-level permission checks** |
| `perform_create(serializer)` | Hook called to save on create |
| `perform_update(serializer)` | Hook called to save on update |
| `perform_destroy(instance)` | Hook called to delete |

## Level 3: concrete generic views

DRF pre-combines the mixins into ready-made classes. This is the same API as above, complete:

```python title="players/views.py"
from rest_framework import generics, permissions

from .models import Player
from .serializers import PlayerSerializer


class PlayerList(generics.ListCreateAPIView):
    queryset = Player.objects.select_related("team", "owner")
    serializer_class = PlayerSerializer
    permission_classes = [permissions.IsAuthenticatedOrReadOnly]

    def perform_create(self, serializer):
        serializer.save(owner=self.request.user)


class PlayerDetail(generics.RetrieveUpdateDestroyAPIView):
    queryset = Player.objects.select_related("team", "owner")
    serializer_class = PlayerSerializer
    permission_classes = [permissions.IsAuthenticatedOrReadOnly]
```

The URLs don't change. From ~45 lines to ~15.

| Class | Methods |
|---|---|
| `ListAPIView` | GET (list) |
| `CreateAPIView` | POST |
| `RetrieveAPIView` | GET (one) |
| `UpdateAPIView` | PUT, PATCH |
| `DestroyAPIView` | DELETE |
| `ListCreateAPIView` | GET (list), POST |
| `RetrieveUpdateAPIView` | GET, PUT, PATCH |
| `RetrieveDestroyAPIView` | GET, DELETE |
| `RetrieveUpdateDestroyAPIView` | GET, PUT, PATCH, DELETE |

### Common customisations

**Only the current user's objects:**

```python
class MyPlayers(generics.ListCreateAPIView):
    serializer_class = PlayerSerializer
    permission_classes = [permissions.IsAuthenticated]

    def get_queryset(self):
        return Player.objects.filter(owner=self.request.user)

    def perform_create(self, serializer):
        serializer.save(owner=self.request.user)
```

**Look up by something other than pk:**

```python
class TeamDetail(generics.RetrieveAPIView):
    queryset = Team.objects.all()
    serializer_class = TeamSerializer
    lookup_field = "name"        # path("teams/<str:name>/", TeamDetail.as_view())
```

**Different serializers for reading and writing:**

```python
def get_serializer_class(self):
    if self.request.method in ("POST", "PUT", "PATCH"):
        return PlayerWriteSerializer
    return PlayerReadSerializer
```

**Filter from the URL** (players of one team, `/api/teams/3/players/`):

```python
class TeamPlayers(generics.ListAPIView):
    serializer_class = PlayerSerializer

    def get_queryset(self):
        return Player.objects.filter(team_id=self.kwargs["team_pk"])
```

## Function view, APIView or generic?

| Situation | Best choice |
|---|---|
| Standard CRUD on a model | Generic views, or a ViewSet |
| Custom, non-CRUD logic | `APIView` or `@api_view` |
| A quick one-off endpoint | `@api_view` |
| Many related endpoints for one model | ViewSet + router ([next chapter](/learn/viewsets-routers)) |

## Summary

- `APIView`: write `get()`, `post()`... yourself; full control.
- `GenericAPIView` + mixins: shared attributes (`queryset`, `serializer_class`) and ready actions.
- Concrete generics (`ListCreateAPIView`, `RetrieveUpdateDestroyAPIView`): CRUD with almost no code.
- Customise with `get_queryset()`, `get_serializer_class()`, `perform_create()`, `lookup_field`.

<details>
<summary>Where do you set <code>owner=self.request.user</code> in a <code>ListCreateAPIView</code>?</summary>

In `perform_create(self, serializer)`: `serializer.save(owner=self.request.user)`.
</details>

<details>
<summary>Why override <code>get_queryset()</code> instead of setting <code>queryset</code> when filtering by the current user?</summary>

The `queryset` attribute is written at class level, where no request exists yet. `get_queryset()` runs for every request, so it can use `self.request.user`.
</details>
